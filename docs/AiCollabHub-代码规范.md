# AiCollabHub 代码规范

适用于服务端 Python/FastAPI，以及用户端、管理端 Vue/TypeScript。默认约束新增和修改的代码，历史代码随实际改动逐步整理。

## 1. 命名

| 对象 | Python | TypeScript / Vue |
| --- | --- | --- |
| 变量、参数、函数 | 下划线：`application_id`、`save_application()` | 小驼峰：`applicationId`、`saveApplication()` |
| 类、类型、接口 | 大驼峰：`ApplicationService` | 大驼峰：`ApplicationInfo` |
| 常量 | 全大写下划线：`MAX_PAGE_SIZE` | 全大写下划线：`MAX_PAGE_SIZE` |
| 布尔变量 | `is_visible`、`has_permission` | `isVisible`、`hasPermission` |
| 普通代码文件 | `application_service.py` | `applicationService.ts` |
| Vue 组件 / 页面 | — | `ApplicationCard.vue` / `ApplicationsView.vue` |
| 组合式函数 | — | `useApplications.ts` |

- 名称表达业务含义，避免拼音和 `data1`、`obj2` 等模糊名称。
- 不使用 C++ 中的 `m_`、`sName`、`nCount` 等作用域或类型前缀。
- 集合使用复数，例如 `applications`；CSS 类使用短横线，例如 `application-card`。
- 前后端 JSON 字段使用小驼峰。已有接口字段、状态值和数据库列名不能因整理代码而随意更改。

### 数据库与接口命名

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 数据表 | 英文复数、小写下划线；复合名称的主体使用复数 | `users`、`auth_sessions`、`operation_logs`、`iam_sync_receipts` |
| 数据库字段、Python ORM 属性 | 英文小写下划线，不使用驼峰或带引号的大小写名称 | `display_name`、`user_sync_time`、`record_type` |
| ORM 模型类 | 英文单数、大驼峰 | `User`、`AuthSession`、`OperationLog`、`IamSyncReceipt` |
| 主键、关联编号 | 主键统一为 `id`；关联字段为实体单数加 `_id` | `id`、`user_id`，不用 `users_id` |
| 平台日期时间 | 使用 `_at` 后缀，类型为带时区的日期时间 | `created_at`、`updated_at`、`expires_at`、`revoked_at` |
| 布尔、摘要字段 | 布尔使用 `is_`/`has_`；摘要使用 `_hash` | `is_enabled`、`has_permission`、`token_hash`、`payload_hash` |
| 平台接口 JSON 字段 | 小驼峰，由接口模型显式映射 | `display_name` → `displayName`、`user_id` → `userId` |
| 枚举值 | 项目自有值使用英文小写，多个单词用下划线 | `active`、`admin`、`ticket_revocation` |

- 使用有业务含义的模块前缀，如 `auth_`、`iam_`；不增加 `t_`、`tbl_` 或项目名等无业务含义前缀，避免保留字表名如 `user`。
- 本平台公开 JSON 契约使用小驼峰，数据库与 Python 内部使用下划线，通过已有接口模型/别名机制映射；不能对第三方报文做不加区分的自动改名。
- IAM 等第三方接口保持其原有字段和枚举值，例如 `appId`、`syncTime`、`userlinkedrole`；接入层负责与内部字段对应，不修改甲方协议。
- 第三方原始时间戳与平台日期时间分开：本次已确认的 `sync_time`、`user_sync_time`、`role_sync_time` 使用 `bigint` 保存 IAM `syncTime` 原值。注明来源及秒/毫秒等单位；协议未明确时标注待确认，不用本地接收时间代替。
- 主键、唯一约束、检查约束、外键和索引遵循后端 `app/db/base.py` 的现有命名约定：`pk_<table>`、`uq_<table>_<column>`、`ck_<table>_<rule>`、`fk_<table>_<column>_<referred_table>`、`ix_<table>_<column>`；复合约束或部分索引使用能说明字段或用途的后缀。手写 DDL 显式命名时也遵循该约定。
- 新表及尚未落地的设计按以上规则命名。已落地的表、列和已有接口不因规范整理直接重命名；需要调整时，随对应任务明确迁移、兼容与回滚方案。

## 2. 格式

- Python 使用 **4 个空格**缩进；TypeScript、Vue、CSS、JSON 使用 **2 个空格**，不用 Tab。
- Python 格式以项目 Ruff 配置为准；TypeScript 默认单引号、省略可选的行尾分号。
- 一行表达一条主要语句，复杂条件和较长对象分行书写，避免多层三元表达式。
- 文件使用 UTF-8，保留末尾换行；编辑时避免产生无关的整文件格式变化。

## 3. 中文注释

- 新增或修改的公共类、业务函数、接口方法补充中文说明。
- 注释说明职责、参数含义和重要限制；复杂逻辑解释“为什么这样处理”。
- 简单函数写一句说明即可；参数、返回值或异常容易误解时再补充详细注释。
- 不逐行复述代码，不保留大段注释掉的废弃实现。

Python 使用 docstring：

```python
def calculate_page_offset(page: int, page_size: int) -> int:
    """计算分页偏移量；页码从 1 开始，参数须已通过正整数校验。"""
    return (page - 1) * page_size
```

TypeScript 使用 JSDoc：

```typescript
/** 计算分页偏移量；页码从 1 开始，参数须已通过正整数校验。 */
export function calculatePageOffset(page: number, pageSize: number): number {
  return (page - 1) * pageSize
}
```

有用的业务注释示例：

```typescript
// 只接收当前请求的结果，避免切换应用后旧响应覆盖新页面。
```

## 4. 基本编码要求

- **明确类型**：Python 公共函数标注参数与返回类型；TypeScript 避免使用 `any` 绕过检查。
- **职责清楚**：后端路由接收请求，服务处理业务；前端页面组织交互，公共逻辑按需提取。
- **复用已有代码**：接口请求、登录校验、数据库访问和公共组件优先使用项目现有实现。
- **处理失败状态**：不能吞掉异常或把失败显示成成功；前端请求要处理加载和错误，保存失败保留输入。
- **防止误操作**：提交中禁止重复点击；权限和数据校验必须在后端落实。
- **保持代码整洁**：删除本次改动产生的无用导入、变量、调试输出和废弃代码，不顺带修改无关功能。
- **改完进行检查**：后端运行相关 Ruff 检查与测试，前端运行类型检查或构建；按改动验证相关功能，如实说明未验证项。

## 5. 资源主表设计

适用于数据集、模型库、场景应用、知识库、AI 工具五类资源的主表，不套用到用户、认证、日志等其他业务表。数据集与场景应用的定稿字段见 [资源主表设计](AiCollabHub-资源主表设计.md)；其他模块按实际页面与业务来源逐项设计，不照搬这两张表的专属字段。

### 职责与字段归属

- 五个模块分别维护自己的主表，不合并为通用资源主表；模块主表不增加 `resource_type`。收藏、用户评价、关注和审核记录可以共用，通过资源类型和对应编号定位对象。
- 主表保存资源基本资料和当前正式展示的概览内容，兼顾列表、搜索与管理需要。页面显示的版本、统计、关联资源和外部运行状态由接口组合，不因出现在概览页就全部复制进主表。
- 字段逐项说明名称、中文名称、类型、空值、来源和业务含义。固定业务含义明确建列；标签等多值项使用结构化数组，不能将整页资料放入一个不受约束的 JSON。
- `summary` 保存简介，`description_markdown` 保存详细说明。`contact` 中文名称为“联系人”，只保存联系人姓名；联系方式有需求时单独设计。`provider_name` 表示提供单位，与关联平台用户的 `creator_id` 分开。
- 资源主键使用 UUID `id`，在版本更新时保持不变；名称不默认设全局唯一。数据库列与 Python 属性使用 snake_case，JSON 契约按已有规则映射，不能随数据库整理直接更改现有 API 字段。

### 状态与版本

- 主表统一使用 `status`：`enabled` 为启用，`disabled` 为禁用，默认 `disabled`。新设计不使用 `listing_status`、`listed`、`unlisted`；主表状态不代表审核结论、访问权限或外部服务是否可用。
- 当前审核状态在各模块发布申请表的 `review_status` 中维护：`pending`、`approved`、`rejected`。草稿尚未进入审核时可为空；共用 `resource_reviews` 保存关联到具体发布申请的历次审核人、结论、意见和时间。申请编辑阶段的完整流程另外设计。
- 主表通过 `current_version_id` 指向当前正式展示的版本，不重复保存可独立修改的版本号；关联建立前允许为空，启用时必须指向本资源已通过审核的版本，不能凭字符串排序选择当前版本。
- 草稿和待审核修改保存在发布申请中，不覆盖当前公开资料。正式发布时，在同一个事务中更新主表概览和当前版本关联；审核通过本身不等于自动启用资源。

### 统计、空值与约束

- 收藏数、评价人数和平均评分由共用明细表统计，主表不保存这些汇总列，也不保存当前用户是否收藏或其个人评分。初期使用批量聚合及 Redis 缓存；确有性能依据时另行设计可由明细重建的汇总，不把缓存作为事实来源。
- 区分数据规模与平台互动统计：数据集的 `record_count`、`data_size_bytes` 是当前版本的规模资料，可以保存已审核发布资料或明确工具链来源的快照；数据集质量评分与用户平均评分分别按各自来源获取。
- 数量、大小未知时使用 `NULL`，真实为零时才保存 `0`；字节数和记录数使用非负整数。无用户评分时接口返回空值。JSONB 数组默认 `[]`，校验元素类型、去空和去重；可扩展业务选项按字典维护，不随意固化为数据库枚举。
- `created_at`、`updated_at` 使用 `timestamptz`；前者表示本地主表记录创建时间，后者仅随主表资料或启用状态变化更新。收藏、评价等互动不改写资源资料的更新时间。
- 使用主键、适用的外键、状态检查与非负约束保障已确认的规则；当前版本必须属于当前资源。索引按实际筛选、排序和关联查询设计。共用表的资源编号无法直接外键关联五张主表，需要统一的存在性、权限与删除关联处理。

设计定稿与实际落库分别记录。本规范规定新设计的目标，既有代码与数据在对应实施任务中迁移；不因规范更新自动执行建表、数据库迁移或恢复此前暂存的重构。

## 6. 模块专属资料设计

适用于场景应用使用说明、数据集字段清单与数据样例，以及模型库、知识库、AI 工具各自的专属资料。本节确定数据归属、存储方式和发布约束；具体子表及完整字段在对应模块实施时按实际需求设计，不要求每个详情页标签单独建表。

### 资料归属与存储选择

- 模块主表继续保存已定稿的基本资料和当前概览。使用说明、字段清单、样例等随内容版本变化的资料归所属模块的发布申请和版本，不追加到共用收藏、评价、下载或审核表，也不塞入主表的通用扩展字段。
- 主表已有的 `description_markdown` 表示资源详细说明；使用步骤、调用参数和数据预览有各自的业务含义，不复用该字段混存。后端按当前版本组合详情页响应，前端页面分栏不决定数据库分表。
- 单段正文使用 Markdown 文本；有限且整体读取的结构化资料可以放在发布申请 `data` 和版本 `snapshot` 的明确字段下。JSONB 必须有对应的类型模型和校验，不作为任意键值容器。
- 资料需要独立筛选、分页、关联约束或处理大量明细时，建立模块专属子表；用关系型列承接可查询字段。只有明确需求才拆表，不为形式统一预建所有模块的附属表。
- 文件本体存 MinIO 或由外部工具链管理，数据库保存文件编号、必要元数据及可定位内容版本的引用。图片、视频、文档和完整数据文件不以 Base64 或二进制写入业务 JSON。

| 专属资料 | 默认保存方式 | 拆分或扩展条件 |
| --- | --- | --- |
| 场景应用使用说明 | 申请资料中的 Markdown 正文，发布时固化到对应版本快照；图片和文档保存文件引用。 | 需要独立维护、检索多个章节时再设计章节子表，并关联版本。 |
| 场景应用操作步骤、调用示例 | 有类型约束的步骤或示例数组，随申请提交并随版本固化；保留阅读顺序。 | 需要独立分页、检索或约束时拆为版本子表。 |
| 数据集字段清单 | 有类型约束的字段数组，记录字段标识、名称、类型、说明、可空性等；保存来源字段顺序。 | 字段量大或需要独立查询、唯一约束时设计 `dataset_fields` 等子表，关联具体版本。 |
| 数据集数据样例 | 仅保存有明确行数、单元格大小及总大小限制的预览数据；与同一版本的字段定义对应。 | 较大样例存文件并记录引用；外部在线预览经工具链接口按需获取，不将完整数据集落入样例字段。 |
| 模型库、知识库、AI 工具专属内容 | 依据实际内容在文本、受约束的结构化资料、版本子表和文件引用中选择。 | 字段来源、读写方式和独立生命周期明确后设计，不能仅因页面相似照搬其他模块。 |

### 草稿、审核与正式版本

- 发布表单中的专属资料先保存到所属模块发布申请的 `data`，与概览资料一起校验和提交。草稿允许不完整；必填、类型、长度、条数及文件有效性在提交时完整校验。
- 提交后冻结本轮业务内容及其附件引用，审核记录的 `submission_snapshot` 对应该轮内容。驳回后的编辑不覆盖此前审核快照；已通过申请保持不变，新修改走新的申请。
- 正式发布时，将专属内容固化到版本 `snapshot` 或该版本的子表，并与主表概览、`current_version_id`、申请发布结果在同一数据库事务中写入。并发审核、重复发布和基线版本冲突沿用共用发布流程处理。
- 正式版本资料不可原地覆盖。展示当前资料时先确定 `current_version_id`，展示历史资料时使用指定的版本编号；不得将旧版说明、新版字段和最新在线样例拼成一个历史版本。
- 同一份专属资料明确唯一的维护入口：保存于 `snapshot` 的内容从快照读取；保存于版本子表的内容通过该版本读取，快照保存必要的稳定引用。为查询建立的派生副本必须随版本生成且可以重建，不能形成可各自编辑的两份事实数据。
- 数据库事务不能回滚 MinIO 文件操作。文件先上传并完成有效性检查，申请保存引用；数据库发布失败时不得删除其他申请或版本仍在引用的文件，未引用临时文件按保留期清理。

### 子表关联、顺序与字段约束

- 专属子表按所属模块和业务内容命名，如 `dataset_fields`、`application_instructions`；名称是命名示例，不表示已经确定必须建表。主键统一使用 UUID `id`。
- 已发布资料子表使用非空 `version_id` 外键关联所属模块版本表，不只关联资源主表。若确需额外保存 `dataset_id`、`application_id` 等资源编号，必须保证资源与版本归属一致。
- 默认使用申请 `data` 保存待审内容。确需拆分大型草稿明细时，使用关联 `publication_id` 的申请明细，并随提交冻结；不得用缺少版本归属的正式资料记录承接草稿。
- 子表字段按现有命名、类型、中文说明和约束规范设计。独立可编辑记录按生命周期设置时间字段；不可变的版本资料不机械增加可修改状态、`updated_at` 或重复审核状态。
- 操作步骤、字段列序和样例行序属于内容含义，需要保留。JSON 数组使用原有次序；子表需要显式顺序时使用非负 `position`，并在版本及所属分组范围内设置必要约束。这不增加资源主表的列表排序字段，主表列表排序仍按前端选择由查询完成。
- 数据集字段标识在同一版本的同一表或结构内唯一，不能要求多表数据集的所有字段全局唯一。样例按字段标识或明确的列对应关系关联字段，不以可重名的中文显示名称作为唯一键。
- JSON 文档明确允许字段、数据类型、空值含义、元素数量和大小限制。数据库列和 Python 属性使用 snake_case，平台接口字段使用小驼峰并显式映射；第三方原始字段名和数据集中真实列名保持原值。

### 外部来源与历史可还原性

- 每项资料注明是用户填写、外部接口获取还是平台生成，并明确是否随发布冻结。外部接口能力尚不明确时不臆造必填外部编号，也不把当前 Mock 值固化为数据库枚举。
- 外部动态预览和运行状态与正式发布快照分开。需要保证历史可还原的资料，保存已审核快照或可以读取的不可变外部版本引用；外部不支持读取历史版本时，接口明确不可用，不能用最新数据冒充历史数据。
- 已发布和历史审核资料引用的文件必须可定位到不可变内容；避免覆盖相同对象导致旧版本附件变化，清理前检查所有申请、审核及版本引用。临时下载链接按访问权限即时生成，不保存为永久附件地址。

本节只更新设计规范，不执行建表、迁移或业务重构。具体模块落地时验证草稿隔离、审核快照、版本切换、失败回滚和附件引用的一致性。
